04FIELD GUIDE

A failure is a
learning opportunity.

Understand what this lab measures, what Kubernetes changes, and where the limits are.

BUILT TO UNDERSTAND, NOT JUST TO BREAK.
What makes a request “good”?

A good request returns HTTP 2xx within 300 ms. The lab aims for 99% good requests in the current rolling window. Error budget is the remaining allowance for bad requests in that window. This is a learning signal, not a production SLA or a long-term SLO assessment.

What changes when I use Kubernetes?

Local mode demonstrates latency and HTTP failures. A readiness fault changes the health endpoint locally, but only Kubernetes uses it to remove the pod from service traffic. Liveness experiments are available only in Kubernetes, where the kubelet can restart the container. The lab observes HTTP behavior; it does not claim to measure pod restart counts.

What does an evidence report include?

Each JSON report contains the environment, scenario, timestamps, actual request samples, event history and separate baseline, impact and recovery summaries. Recovery time is an observation within a bounded recovery phase; a missing value does not prove recovery happened. Export reports before restarting the controller.

How are experiments contained?

The controller targets one configured demo service. Write actions require a control key, and the target automatically expires injected faults after at most 60 seconds. There is no arbitrary URL input, shell execution, Kubernetes API access or cluster-wide disruption. Use a dedicated local lab environment.
